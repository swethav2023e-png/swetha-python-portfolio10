SYSTEM ARCHITECTURE
Data Flow: Ingestion to System Health Intelligence
1. Multi-Format Ingestion
Accepts JSON Format A ('errors' array), Format B (flat array), Syslog, Apache/Nginx web logs, and raw exceptions. Enforces SHA256 idempotency deduplication.
2. Subsystem Classifier
Categorizes logs into 9 identifiable components (API, Database, Auth, Network, Jobs, Infra, Memory, Filesystem, Application). Normalizes severities.
3. Analytical Intelligence
Calculates evidence-based Health Score (0-100), statistical z-score volume spikes, burst anomalies, subsystem failure rates, and historical baseline delta %.
4. Reporting & UI Console
Serves 10 dedicated observability views, reactive Chart.js dashboards, and generates 10-section executive reports via JSON and Markdown export.

HEALTH SCORING
Evidence-Based System Health Scoring (0–100)
Mathematical Formulation
RawPenalty = (12 * N_critical + 4 * N_error + 1.5 * N_warning) * DensityWeightTotalPenalty = RawPenalty + AnomalyPenalty + ConcentrationPenaltyHealthScore = max(0, min(100, round(100 - TotalPenalty)))
Contributing Factors:
• Severity Weights: Critical (12 pts), Error (4 pts), Warning (1.5 pts)
• Issue Density: Multiplied by (N_issues / N_total) to scale with volume
• Anomaly Penalty: +5 to +10 pts when volume spikes or bursts occur
• Concentration Penalty: +5 pts if >65% failures hit a single subsystem
• Data Caveat: Shows explicit 'Insufficient Data' state if 0 records exist
System Health Status Tiers
[90 – 100] EXCELLENT: System healthy; minimal warnings; optimal operation.
[75 – 89] GOOD: Normal operational load; isolated errors handled gracefully.
[50 – 74] FAIR: Elevated warning/error rates; targeted investigation needed.
[25 – 49] DEGRADED: High failure density or recurring critical events.
[0 – 24] CRITICAL: Cascading subsystem failures; immediate intervention required.
[N/A] INSUFFICIENT DATA: Provisional state when 0 logs exist; no fabricated numbers.

ANALYTICS & RISKS
Subsystem Tracking & Statistical Anomaly Detection
Component Risk Ranking
Logs mapped to 9 distinct components:• API & Backend• Database & Storage• Authentication & Security• Network & Gateways• Background Jobs & Workers• Infrastructure & System• Memory & GC• File System• Application CoreEach ranked by failure rate %, event volume, and relative risk score.
Statistical Anomaly Engine
Detects true anomalies without ML bloat:1. Volume Spikes (Z-Score):Flags time buckets where event count exceeds mean + 1.5 * standard deviation.2. Critical Bursts:Identifies velocity clusters of high-severity failures.3. Concentration Risks:Alerts when >65% of failures isolate to a single subsystem.
Historical Comparisons
Compares active sessions against stored baselines:• Volume Delta % (+/-)• Newly Emerged Error Signatures• Resolved Error SignaturesAllows DevOps teams to immediately determine whether recent deployments caused degradation or stability improvements.

Slide 8
CLOUD INFRASTRUCTURE
Vercel Serverless Architecture & Storage Compatibility
Ephemeral Storage Protection
Vercel Serverless runs on a read-only filesystem except for /tmp.LogHealth dynamically inspects the environment (VERCEL=1) and initializes SQLite inside tempfile.gettempdir() (/tmp/loghealth.db), completely eliminating read-only crashes.
Durable Database Abstraction
Built on the DatabaseManager repository pattern.Allows production environments to effortlessly connect external PostgreSQL databases (Supabase, Neon, Railway) simply by setting DATABASE_PATH in Vercel settings, without any application code rewrite.
Zero-Dependency Frontend
Built entirely on Vanilla HTML5, CSS3, and JavaScript.Zero Node build step or npm bundle bloat on Vercel. Static assets are served instantly via edge CDN with Chart.js loaded asynchronously for ultra-fast Time to Interactive (TTI).
